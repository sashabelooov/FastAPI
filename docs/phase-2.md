# Phase 2 — User Model + Auth (Email/Password + JWT)

## What we built
Full authentication system: user registration, login with JWT tokens, and protected routes.

## File creation order

### 1. `app/models/user.py`
SQLAlchemy model mapping to the `users` table.
Fields: `email` (unique, indexed), `full_name`, `hashed_password`, `is_active`, `is_verified`.
Inherits `id`, `created_at`, `updated_at` from `TimeStampedBase`.

### 2. `app/models/__init__.py`
Imports all models so Alembic can discover them via `Base.metadata`.
Add every new model here — `env.py` never needs to change.

### 3. `migrations/env.py` (updated)
Added `import app.models` to register all models with `Base.metadata` before Alembic runs.

### 4. `migrations/versions/xxxx_create_users_table.py`
Generated by `alembic revision --autogenerate -m "create users table"`.
Creates the `users` table and `ix_users_email` unique index.

### 5. `app/schemas/user.py`
Two Pydantic schemas:
- `UserCreate` — request body for registration: `email`, `full_name`, `password`
- `UserResponse` — response shape: everything except `hashed_password`. Uses `from_attributes = True` to read from SQLAlchemy objects.

### 6. `app/core/security.py`
Password hashing and JWT utilities:
- `hash_password` / `verify_password` — using `bcrypt` directly (not passlib)
- `create_access_token(subject)` — short-lived (30 min), payload: `sub`, `exp`, `type: access`
- `create_refresh_token(subject)` — long-lived (7 days), payload: `sub`, `exp`, `type: refresh`
- `decode_token(token)` — decodes and returns the payload dict

### 7. `app/repositories/user.py`
Database access layer for users:
- `get_by_email(session, email)` → `User | None`
- `get_by_id(session, user_id)` → `User | None`
- `create(session, data)` → `User` (hashes password, commits, refreshes)

### 8. `app/services/auth.py`
Business logic layer:
- `register` — checks email uniqueness, creates user, returns `UserResponse`
- `login` — verifies credentials (same error for wrong email and wrong password), returns token pair

### 9. `app/core/dependencies.py` (updated)
Added `get_current_user` dependency:
- Reads `Authorization: Bearer <token>` header via `OAuth2PasswordBearer`
- Decodes JWT, validates `type == "access"`, looks up user in DB
- Returns `User` or raises `401`

### 10. `app/api/v1/endpoints/auth.py`
Three endpoints:
- `POST /api/v1/auth/register` → 201 + `UserResponse`
- `POST /api/v1/auth/login` → `{access_token, refresh_token, token_type}`
- `GET /api/v1/auth/me` → `UserResponse` (protected)

### 11. `app/api/v1/router.py`
Main API router with prefix `/api/v1`. Includes the auth router.

### 12. `app/main.py` (updated)
Added `app.include_router(api_router)`.

## Key decisions

| Decision | Reason |
|----------|--------|
| `bcrypt` directly, not `passlib` | passlib is abandoned and broken with bcrypt >= 4.0 |
| `PyJWT` not `python-jose` | More actively maintained, simpler API |
| Same error for wrong email and wrong password | Prevents user enumeration — attacker can't tell which one is wrong |
| `type` claim in JWT payload | Refresh tokens must not work as access tokens |
| `get_current_user` raises one generic 401 for all failures | Don't leak why validation failed |
| `user_repository` and `auth_service` as module-level singletons | No state on the class — one instance is enough (SSOT) |
| `hashed_password` excluded from `UserResponse` | Never send password data back to the client |

## Principles applied
- **SoC** — route handles HTTP, service handles business logic, repository handles DB
- **Defensive Programming** — same error for bad credentials, generic 401 for token failures, password never returned
- **DRY** — `get_current_user` reused across all protected routes
- **SSOT** — `user_repository` and `auth_service` singletons, token config in `settings`
- **Fail Fast** — `401`/`400`/`403` raised immediately with clear messages
